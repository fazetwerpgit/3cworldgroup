# Security hardening, 2026-07-25

Branch `security/close-open-routes`. Nothing pushed, nothing deployed.

## Read this first

Two findings were more serious than the ones that prompted the work, and the
audit that started it was wrong in both directions. The method that produced
correct answers was: **follow the call chain, then probe a running server.**
Grepping route files for auth-helper names produced false positives *and* false
negatives, and cost most of a night's rework.

## What was actually wrong

### 1. CRITICAL — the management gate did not authenticate

`src/lib/auth/requireManagement.ts` exported `requireManagement`,
`requireAdmin`, `requireSelfOrManagement` and `getRequester`. Every one took a
`userId` **string**, not a request. No token verification anywhere. Its own
docstring said so:

> The portal's API routes trust a client-supplied userId and resolve the
> caller's role from Firestore (there is no session-token verification layer).

18 routes gated on it, including sale approval, user creation and user editing.
Anyone who knew an admin's Firebase uid could pass it as `?requestedBy=` and be
that admin.

**Obtaining an admin uid took one request.**
`GET /api/portal/chat/channels/[channelId]/members` returns
`{ uid, name, role, ... }` for every member, where `role` is the display label —
"Admin", "Operations". The all-company channel contains every active user. So
any employee received a labelled directory of every colleague's uid and role,
picked an admin, and used it. Independent corroboration: chat message documents
carry `authorId` **and** `authorRole`; the leaderboard returns real uids with a
caller-controlled limit the UI already sets to 1000.

Any employee → full admin, in two requests. No guessing.

**Fixed:** all 18 routes migrated to token-verified helpers; the module deleted.

### 2. CRITICAL — decommissioning did not revoke access

`pipeline/decommission` set Firestore `status: 'inactive'` and wrote an audit
trail. It never disabled the Firebase auth account, never revoked refresh
tokens, and never cleared `role`. The code comment explained that "AuthContext
blocks non-active sign-ins" — but `AuthContext` is React, running in the
browser. It is not a security boundary.

A fired employee's account still accepted their password, so they could mint
fresh ID tokens indefinitely. Because `role` survived, a decommissioned **admin**
still passed `requireVerifiedAdmin`.

The same flag-only pattern deactivated admin and operations accounts in
`auth/users/[id]`.

**Fixed:** both paths now disable the auth account and revoke refresh tokens,
and re-enable on reinstate. The API layer also rejects non-active accounts, so
existing tokens stop working regardless.

> That last sentence was **false when first written** and is true now. Two
> handlers had a private copy of `verifyCaller` that checked the token but never
> read `status`, so a deactivated admin kept working there until their token
> expired. Found by the adversarial review; see below.

### 3. HIGH — the API layer was weaker than the database layer

`verifyCaller` admitted any caller whose user document merely *existed*. It never
checked `status`. `firestore.rules` `isApproved()` **did** require
`status == 'active'`. So a self-signed-up bot with a valid token passed every
`requireVerifiedUser` route while being blocked at the Firestore layer.

`requireVerifiedAdmin` did not call `verifyCaller` at all — it duplicated the
body, so a fix to the shared helper would have silently skipped the most
privileged helper in the repo.

**Fixed:** status is checked before role, in one shared path.

### 4. HIGH — 11 routes had no authentication at all

`profile`, `commission` (GET and PUT), `calls`, `pipeline` (×4),
`email-templates`, `recruiting` (×2). Confirmed by probing a running server with
no credentials: they answered `400 "userId is required"` and `404 "User not
found"` — handler-level responses, proving no gate ran.

**Fixed.** `scripts/audit-open-routes.mjs` is the regression test; every row must
read `GUARDED`.

### 5. Firestore rules allowed console-based fraud

`sales`, `training`, `userProgress` and `leaderboard` allowed read and write to
any approved user. A rep could create a sale with `totalPoints: 99999` or delete
a colleague's sale from the browser console, bypassing the server-side point
calculation entirely.

**Fixed but NOT DEPLOYED** — see `docs/security/firestore-rules-deploy.md`.

## What the adversarial review caught

Two Opus agents reviewed the finished diff — one hunting auth bypasses, one
hunting production regressions. Neither wrote any of the code. Between them they
found six things the implementation work missed, two of which were regressions
this branch itself introduced.

### 6. HIGH — `/api/portal/training` was open to the internet

`GET /api/portal/training` answered `200` with the full catalogue to an
unauthenticated `curl`. The gate was conditional on `?all=true`, and a comment
claimed the listing was open "by design (reps and the public read it)" — the
"public" half had no basis; no public page calls it.

`GET /api/portal/training/[id]` was worse: no gate **and** no `isPublished`
filter, so any id returned unpublished drafts. The PUT and DELETE in that same
file were migrated; the GET was left behind.

**The method failure matters more than the bug.** `scripts/audit-open-routes.mjs`
probes a list of paths *I hand-wrote*. `/api/portal/training` was never in it. So
"0 of 17 routes answer without credentials, exit 0" was true and simultaneously
missed the one portal route that did. **A green audit proves the listed routes
are gated — nothing more.** The list is now 19 and derived against the real route
table, but it is still a list.

**Fixed** (`c2972a1`, `d005682`): both reads gated, `[id]` 404s on
unpublished-and-not-management so a draft's existence isn't confirmed, client
updated, both paths added to the audit.

### 7. HIGH — two handlers bypassed the account-status gate entirely

`settings/weekly-challenge` and `sales/company-stats` each carried a private
`verifyCaller` copy. They verified a real ID token but never read the user doc's
`status`. They were missed because they never imported from `requireManagement.ts`,
so they were not on the migration list — and they *looked* gated.

Consequences: an unapproved self-signup got in (exactly the account class commit
`c2e2c43` exists to keep out), and a deactivated admin kept working for up to an
hour, because this branch's entire revocation answer *is* the Firestore status
check they skipped.

**Fixed** (`ef3d040`): both copies deleted, replaced with the shared helpers. The
weekly-challenge PUT's manual `role !== 'admin'` check went too — `requireVerifiedAdmin`
does that *and* checks status.

### 8. REGRESSION — a new hire's notification bell was dead on every page

All four notification gates rejected `pending`. `PortalHeader` calls
`useNotifications()` unconditionally and is mounted on nearly every portal page.
`useNotifications.ts:44` is `if (response.ok)` with no `else`, so the 403 was
discarded — no banner, no console line, bell permanently empty.

Every "document approved" and "item rejected, resubmit" alert the onboarding flow
sends would have been invisible to exactly the person it was addressed to, for
the whole period they are pending — the only period those alerts are sent.

Caused by this branch: master's `requireSelfOrManagement` did no status check.

**Fixed** (`1b51f9e`). All four confirmed self-scoped first; the management
dispatch gate stays active-only.

### 9. REGRESSION — a new hire could open training but not record finishing it

`training/progress` lacked the opt-in the training *reads* received in `c2972a1`
— a self-inconsistency introduced hours apart on the same night. Silent twice:
progress read as 0% (indistinguishable from "nothing completed"), and
`markComplete` returned `false`, which the page discards, so the button appeared
to work and did nothing.

**Fixed** (`5f99d53`).

### 10. MEDIUM — the leaderboard rebuilt the roster-enumeration primitive

`limit` was caller-controlled with no ceiling, and each row carries a real uid
plus a name. A hired-but-not-yet-activated rep — admitted so the dashboard
renders — could pull a complete company directory with `limit=1000`. That is the
same primitive that made finding #1 a two-request exploit rather than a guessing
game.

**Fixed** (`2702dc6`): non-management capped at 100. The two admin pages that
legitimately want the whole company still get it. Capping was chosen over
dropping the opt-in, which would have blanked the dashboard for every new hire —
trading one regression for another.

### 11. The test suite could not fail on the distinction that matters

Nothing asserted that a management *field* role is **not** `isManagement`.
`sales/route.ts` uses `gate.isManagement` to decide whether a caller may filter
by someone else's `salesRepId`. `isManagerOrAbove` is the more natural-sounding
name — swap it in and every `l1_manager` could read every rep's customer PII,
with the whole suite still green.

**Fixed** (`210f119`): +10 tests, including that pair, `requireVerifiedRequester`'s
full triple, and assertions that the bare token actually reaches `verifyIdToken`.
Both new PII tests were confirmed to go red before being committed green.

## What was fine — retracted false alarms

Recorded because an early draft of this audit claimed otherwise:

- **The six `forms/*/review` routes were never open.** They gate on
  `requireVerifiedManagement` via `src/lib/forms/reviewQuery.ts`, stamp the
  reviewer from the token, and use a transaction so two clicks cannot both flip
  `new → handled`. **Payroll dispute PII was never exposed.**
- **Onboarding invite tokens are strong** — 256 bits from `crypto.randomBytes`,
  stored SHA-256 hashed, looked up by hash, 14-day expiry, single-use for
  submission.
- **The public upload route is well defended** — MIME allowlist, 4 MB cap,
  extension derived from validated MIME rather than the filename, and a
  server-derived storage path so a token holder cannot write into another
  invite's folder.
- The eSign webhook verifies signatures; the cron route checks `CRON_SECRET`;
  `storage.rules` is Admin-SDK-only outside `/training`.

## The onboarding constraint that shaped the design

A hired rep is `status: 'pending'` **with a field role** for the entire
onboarding flow, and is fully signed in — `useRequireAuth` checks role and
permissions but never status, and there is no portal-wide redirect confining
them to `/portal/onboarding`. They browse the ordinary shell.

So a blanket active-only gate would have locked every new hire out of the
portal. The opt-in is deliberately **not** named `allowPending`:

| account state | admitted? |
|---|---|
| `active` | always |
| `pending` **with** a field role — invited, hired, mid-onboarding | only where a route opts in |
| `pending` **without** a field role — unapproved self-signup | never |
| `inactive` — decommissioned | never, opt-in or not |

`allowPending` would have readmitted exactly the bot accounts commit `c2e2c43`
was written to keep out.

**Granted the opt-in:** dashboard reads (leaderboard, sales, sales/stats),
`calls`, `profile` PUT, `commission` GET, push registration, presence, and the
three rep-facing onboarding routes.
**Denied:** `sales` POST, every form submit, `forms/upload`, `forms/options` —
business writes stay active-only.

## Still open — deliberate, not forgotten

1. **No rate limiting anywhere.** Login, signup, and the public application form
   accept unlimited requests. `/api/public/applications` has no captcha,
   honeypot or email-shape validation — `"x"` is accepted as an email.
2. **No security headers or CSP.** No `middleware.ts` exists.
3. **`onboarding/upload` parses the multipart body before its auth gate**,
   because the target userId lives in the form data. Pre-existing, low severity,
   but a free DoS amplifier for an unauthenticated caller.
4. **`reviewQuery` silently truncates at 200 submissions** with no ordering
   guarantee beyond `createdAt desc`. A busy queue hides older items. Workflow
   correctness, not security.
5. **The onboarding token still authenticates GET after submission**, degrading
   to a read-only PII view until the 14-day expiry. Only matters if the link
   leaks.
6. **No Firestore rules tests and no emulator.** There is no automated safety net
   for a rules change.
7. **CSV formula injection** — admin queue pages export CSV, and a name beginning
   `=`, `+`, `-` or `@` becomes a live formula in Excel. React escapes these in
   the UI, so there is no XSS.
8. **Two client call sites race on the auth token.** `auth.currentUser` is
   `undefined` until Firebase restores the session; the race-safe helper
   (`src/lib/firebase/getIdToken.ts`, added in `7f72e65`) awaits
   `onAuthStateChanged`. `useLeaderboard.ts:44` and `useFormOptions.ts:13` read
   `currentUser` directly in a bare `useEffect` with no user guard, so a hard
   refresh can fire before auth resolves.
   **This is live on master today. It is NOT a regression from this branch and
   must not be reported as one** — both routes were already gated before tonight.
   The two fail differently, which matters when looking for them: `useLeaderboard`
   sends no header and produces a visible 401; `useFormOptions` returns early and
   makes no request at all, so the dropdowns are just silently empty. Grepping the
   console for 401s finds one and misses the other.
   Everything this branch added (22 of 22 call sites) uses the safe helper.
9. **`authedFetch` in `admin/page.tsx:25` is typed `(url: string)` with no
   `init`.** Reach for it on a POST and the method and body are silently dropped —
   it becomes a GET. Most obviously-named helper in the repo, most dangerous to
   reuse. Its 3 current call sites depend on it being GET-only, so anyone
   "fixing" the signature must audit those first.

Suggested order: rate limiting, then headers/CSP, then the rest.

### The full route table, audited separately

After finding #6, every route was enumerated rather than trusted to the list.
**69 route files, 109 exported route+method pairs.** Classification:

| | |
|---|---|
| gated by a bearer-token helper | 101 |
| authenticated by another mechanism | 5 (3× hashed invite token, 1× eSign signature, 1× `CRON_SECRET`) |
| intentionally open | 3 (`signup`, `signup-notify`, `public/applications`) |
| **ungated and should not be** | **0** |

All 40 GET pairs were probed with no credentials: **zero 200s**, 36 clean 401s,
and four resolved — three 400 because they validate a `userId` param before the
gate (re-probed with the param: all three 401), and the cron route 500s in dev
because `CRON_SECRET` is unset, which fails **closed**.

**Three limits — this is not blanket clearance:**

1. **69 of 109 pairs were never probed.** Every mutating method is source-read
   only, because probing one means sending a body to a production-backed server.
   Unconfirmed, not cleared.
2. **This answers "is there a check", not "is it the right level".** A route using
   `requireVerifiedUser` where it needs `requireVerifiedManagement` reads as
   GATED.
3. **Dynamic routes got one synthetic id.** A route that behaves differently for a
   *real* id — exactly what `training/[id]` did with unpublished drafts — would
   not be caught by a 404 on a junk id.
